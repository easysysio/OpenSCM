# Design — Compliance Alerting (0.8.0)

**Status:** draft, pending review
**Target release:** 0.8.0
**Author:** Yariv + Claude (design review)
**Last updated:** 2026-08-20

---

## 1. Goal

OpenSCM records hourly compliance history, so the server already *knows* the
moment a policy falls from 94% to 61%. Today that knowledge stays in a chart
until somebody opens the page. Nothing is ever pushed.

Add a first-class **Alerts** section: rules that watch a policy's compliance
score and deliver a notification when it moves.

Decisions locked with the user:

1. **New sidebar section** — Alerts is a top-level menu item, not a tab buried
   inside Settings.
2. **Scope is a policy** — pick one policy (or all policies).
3. **Trigger** — dropped by N points, gained by N points, or crossing a fixed
   percentage.
4. **Actions** — email, webhook, syslog, notify inside OpenSCM.
5. **Each action carries one parameter** — the address it delivers to.

---

## 2. Where alerts are evaluated

**Not on the hourly snapshot tick.** This is the single most important
decision in the design, so it is worth stating why.

`record_entity_history` runs at minute 0 of each hour. If a scheduled policy
run at 14:05 drops a fleet 33 points, an hourly evaluator would alert at 15:00
— 55 minutes late. Worse, if the score recovers at 14:50, the 15:00 snapshot
looks identical to the 14:00 one and **the alert never fires at all**. Hourly
sampling silently loses every excursion shorter than an hour.

Alerts evaluate on the **recalculation**, which is the actual event:

```
scheduler.rs :: run_recalc(pool, tenant)
    ├─ snapshot policy scores BEFORE  (id, compliance_score, score_test, score_system)
    ├─ tx: purge_ghost / test / system / container / policy stats
    ├─ tx.commit()
    └─ snapshot AFTER → evaluate_alerts(pool, tenant, before, after)   ← new
```

`run_recalc` is the sole choke point through which every policy score change
passes — scheduled runs, manual runs, group edits, exclusions, startup. One
hook covers all of them.

**Evaluation happens after `tx.commit()`, never inside the transaction.**
Delivery is network I/O (SMTP, HTTP, UDP). Holding a SQLite write transaction
open across a hung webhook would block every writer in the process.

### 2.1 Startup suppression

`run_recalc(pool, None)` also runs at startup. After a long outage the first
recalc can move hundreds of scores at once and would fire an alert storm —
the same failure shape as the `prune_inactive_systems` data-loss bug fixed in
0.7.6. The startup call passes a `suppress_alerts` flag: the first recalc
after boot updates alert state (so the next real change is measured from a
correct baseline) but delivers nothing.

## 3. Data model

Schema **v37 → v38**. Three tables.

### 3.1 `alerts` — the rule

```sql
CREATE TABLE IF NOT EXISTS alerts (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    tenant_id        VARCHAR(191) NOT NULL DEFAULT 'default',
    name             TEXT    NOT NULL,
    enabled          INTEGER NOT NULL DEFAULT 1,

    -- scope
    scope_type       TEXT    NOT NULL DEFAULT 'policy',  -- 'policy' | 'all_policies'
    policy_id        INTEGER,                            -- NULL when scope_type='all_policies'

    -- trigger
    trigger_type     TEXT    NOT NULL,   -- 'drop' | 'gain' | 'below' | 'above'
    threshold        REAL    NOT NULL,   -- points for drop/gain, percentage for below/above
    score_axis       TEXT    NOT NULL DEFAULT 'test',    -- 'test' | 'system'

    -- action
    action           TEXT    NOT NULL,   -- 'notify'|'email'|'webhook'|'syslog'
    target           TEXT,               -- address; NULL only for 'notify'
    target_secret    TEXT,               -- webhook auth header value

    cooldown_minutes INTEGER NOT NULL DEFAULT 60,

    created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
    created_by       INTEGER,
    FOREIGN KEY (tenant_id) REFERENCES tenants (id)  ON DELETE CASCADE,
    FOREIGN KEY (policy_id) REFERENCES policies (id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_alerts_tenant_enabled ON alerts (tenant_id, enabled);
```

`score_axis` is not optional decoration. This codebase carries two compliance
axes (`score_test` and `score_system` / `score_policy`) and a per-tenant
toggle that flips which one is displayed — the 0.6.6 dual-mode lesson recorded
in `record_entity_history`. An alert that does not name its axis becomes
ambiguous the moment a tenant flips that toggle. The rule pins its axis at
creation time and keeps watching that axis regardless of the display setting.

`policy_id` cascades on policy delete, so deleting a policy removes its alerts.

### 3.2 `alert_state` — edge detection

```sql
CREATE TABLE IF NOT EXISTS alert_state (
    alert_id      INTEGER NOT NULL,
    policy_id     INTEGER NOT NULL,
    last_score    REAL,
    state         TEXT NOT NULL DEFAULT 'ok',   -- 'ok' | 'firing'
    last_fired_at DATETIME,
    PRIMARY KEY (alert_id, policy_id),
    FOREIGN KEY (alert_id)  REFERENCES alerts (id)   ON DELETE CASCADE,
    FOREIGN KEY (policy_id) REFERENCES policies (id) ON DELETE CASCADE
);
```

State is keyed **(alert, policy)** rather than living on the `alerts` row,
because an `all_policies` rule tracks each policy independently. One policy
being below threshold must not suppress the alert for another.

### 3.3 `alert_deliveries` — the outbox and the audit trail

```sql
CREATE TABLE IF NOT EXISTS alert_deliveries (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    tenant_id     VARCHAR(191) NOT NULL DEFAULT 'default',
    alert_id      INTEGER,
    policy_id     INTEGER,
    fired_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    old_score     REAL,
    new_score     REAL,
    action        TEXT NOT NULL,
    target        TEXT,
    status        TEXT NOT NULL DEFAULT 'pending', -- 'pending'|'sent'|'failed'
    attempts      INTEGER NOT NULL DEFAULT 0,
    last_error    TEXT,
    next_retry_at DATETIME,
    FOREIGN KEY (tenant_id) REFERENCES tenants (id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_alert_deliv_retry  ON alert_deliveries (status, next_retry_at);
CREATE INDEX IF NOT EXISTS idx_alert_deliv_tenant ON alert_deliveries (tenant_id, fired_at);
```

`alert_id` is deliberately **not** `ON DELETE CASCADE` — deleting a rule must
not erase the history of alerts it already sent. The column goes NULL and the
row survives with its `action`/`target`/scores intact.

Pruned by a new `alert_history_retention_days` setting, following the existing
`*_retention_days` pattern (0 = keep forever).

## 4. Trigger semantics

Let `prev` = score at last evaluation, `curr` = score now, `T` = threshold.

| `trigger_type` | Fires when                          | Kind          |
|----------------|-------------------------------------|---------------|
| `drop`         | `prev - curr >= T`                  | edge (natural)|
| `gain`         | `curr - prev >= T`                  | edge (natural)|
| `below`        | `curr < T` **and** `prev >= T`      | edge (guarded)|
| `above`        | `curr > T` **and** `prev <= T`      | edge (guarded)|

**Everything is edge-triggered.** `below`/`above` need the explicit `prev`
guard: without it, a policy resting at 60% against an 80% threshold would
deliver an email on every recalculation, forever. That is the classic alerting
failure and it is what makes people turn alerting off. A rule re-arms only
after the score returns to the good side.

### 4.1 The `-1` rule

`compliance_score = -1.0` means *never scanned*, not *zero percent*. A policy
transitioning to or from `-1` (new policy, policy whose systems were all
removed, results purged) must be treated as **no comparison available**:
update `last_score` and skip evaluation entirely.

Without this, a policy going unscanned reads as a 95-point drop and pages
somebody at 03:00 for a bookkeeping change.

### 4.2 Cooldown

After a delivery, that (alert, policy) pair is muted for `cooldown_minutes`
(default 60). This bounds a flapping policy to one message per hour per rule.
Suppressed evaluations still update `last_score` and `state`.

## 5. Actions

All four share one payload struct built once per firing, then rendered per
transport.

### 5.1 `notify` — notify inside OpenSCM

Writes a row to the existing `notify` table through
`add_notification(pool, tenant, "warning", owner, msg)`, one per Admin in the
tenant, surfacing on the bell icon.

**No parameter, no network, cannot fail.** It is a local INSERT in the same
database the evaluation already has open, which makes it the only action with
no delivery semantics to reason about — no timeout, no retry, no queue row, no
SSRF surface. It is the default action offered in the UI and the fallback
recorded when another transport exhausts its retries.

### 5.2 `email`

Existing `Mailer::from_db(pool)` + `send(to, subject, html)`. `target` is a
comma-separated address list. HTML body reuses `report_email_body`'s wrapper
for visual consistency with the existing report mails.

Subject: `[OpenSCM] {policy} compliance {94.2% → 61.0%}`

### 5.3 `webhook`

`POST {target}` with `Content-Type: application/json`, via the existing
`reqwest` client (10s timeout, 3 attempts, exponential backoff 1m/5m/15m).
If `target_secret` is set it is sent as `Authorization: {secret}`, letting the
same field carry `Bearer …`, a Slack signing token, or nothing.

Payload is versioned so downstream consumers can be written against a contract:

```json
{
  "version": 1,
  "event": "compliance.alert",
  "fired_at": "2026-08-20T14:05:11Z",
  "server": "https://scm.acme.io",
  "tenant": "acme",
  "alert":   { "id": 7, "name": "Prod CIS drop", "trigger": "drop", "threshold": 10.0, "axis": "test" },
  "policy":  { "id": 3, "name": "CIS Ubuntu 22.04", "url": "https://scm.acme.io/policies/report/3" },
  "score":   { "previous": 94.2, "current": 61.0, "delta": -33.2 },
  "systems": { "passed": 12, "failed": 19 }
}
```

A raw JSON POST reaches Slack, Teams, PagerDuty, Opsgenie and every internal
automation through one code path. Building four bespoke integrations instead
would be four times the code and four times the breakage surface for the same
result.

### 5.4 `syslog`

RFC 5424 over UDP (default) or TCP, `target` = `host:port`, port defaults to
514. No new dependency — `tokio::net::UdpSocket` plus string formatting is
about 40 lines.

```
<PRI>1 2026-08-20T14:05:11Z scm.acme.io openscm - COMPLIANCE
  [openscm@99999 tenant="acme" policy="3" prev="94.2" curr="61.0"] CIS Ubuntu 22.04 dropped 33.2 points
```

`PRI` = facility 13 (log audit) × 8 + severity, mapped from the size of the
move: ≥25 points → `warning`(4), otherwise `notice`(5); `gain` → `info`(6).

UDP delivery is fire-and-forget and is recorded `sent` on successful socket
write. That is the protocol's guarantee, not a shortcut, and the UI says so.

### 5.5 SSRF containment (SaaS)

In SaaS, `target` is attacker-controlled: a tenant can point a webhook at
`http://169.254.169.254/latest/meta-data/` and read cloud instance metadata
out of the response, or scan the operator's internal network by timing
responses.

When `saas_mode` is on, webhook targets are validated at save
time **and again at delivery time** (DNS can be re-pointed between the two):

- scheme must be `https`
- resolved IPs must not be loopback, link-local (`169.254.0.0/16`,
  `fe80::/10`), private (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`),
  or unspecified
- redirects disabled
- response body discarded, never surfaced to the tenant

`ipnet` is already a dependency. In CE this validation is off by default —
a self-hosted operator legitimately posts to `http://10.0.0.5/hook`.

## 6. Routes and UI

New module `scmserver/src/alerts.rs`, sidebar entry **Alerts** (bell icon)
placed after Reports.

| Method | Path                   | Role     | Purpose                        |
|--------|------------------------|----------|--------------------------------|
| GET    | `/alerts`              | Viewer   | List rules + last-fired column |
| GET    | `/alerts/new`          | Admin    | Create form                    |
| POST   | `/alerts/create`       | Admin    | Insert                         |
| GET    | `/alerts/{id}/edit`    | Admin    | Edit form                      |
| POST   | `/alerts/{id}/update`  | Admin    | Update                         |
| POST   | `/alerts/{id}/toggle`  | Admin    | Enable / disable               |
| POST   | `/alerts/{id}/delete`  | Admin    | Delete rule (history survives) |
| POST   | `/alerts/{id}/test`    | Admin    | Send one synthetic delivery    |
| GET    | `/alerts/history`      | Viewer   | Delivery log, filterable       |

**Admin** to manage, **Viewer** to read: an alert rule carries an SMTP
recipient list and a webhook secret, and it can be used to make the server
emit traffic to an arbitrary address. That is administrative surface.

`/alerts/{id}/test` is not a nicety. A webhook URL typo or a firewalled syslog
port is otherwise invisible until a real incident fails to deliver. The test
button sends a synthetic payload through the real transport and shows the raw
result — status code, error text — inline.

### 6.1 The create form

One page, progressive disclosure, matching the existing test/policy forms:

```
Name          [ Prod CIS drop                    ]
Enabled       [x]

WHEN
Policy        [ CIS Ubuntu 22.04            ▼ ]   (or "All policies")
Compliance    [ drops by ▼ ] [ 10 ] points
              ( drops by / rises by / falls below / rises above )
Measuring     [ Test compliance ▼ ]              (Test / System)

THEN
Action        [ Webhook ▼ ]                      (Notify in OpenSCM / Email / Webhook / Syslog)
Webhook URL   [ https://hooks.example.com/…    ]
Auth header   [ Bearer …                       ]  (optional)
              [ Send test ]

Cooldown      [ 60 ] minutes between alerts for the same policy
```

The unit label after the threshold box switches between "points" and "%" with
the trigger type, because "drops by 10%" and "falls below 10%" mean very
different things and the form should not let that stay ambiguous.

## 7. Delivery, retry, failure

Deliveries are written `pending` **inside** the evaluation, then drained by a
new **TASK G** in the scheduler minute loop. This means:

- a slow webhook never delays a recalculation
- a server restart mid-delivery loses nothing — the row is still `pending`
- retries are naturally rate-limited to the minute tick

Backoff 1m → 5m → 15m, then `failed`. On final failure the rule's owner gets a
`notify` notification saying the transport failed, so a silently broken webhook
becomes visible without needing anyone to read the delivery log.

## 8. Test plan

New `scmserver/tests/alerting.rs`:

1. `drop` fires once on 94→61, not again on 61→60
2. `below` re-arms only after recovery above threshold
3. cooldown suppresses the second firing inside the window
4. `-1 → 85` and `85 → -1` fire nothing
5. startup recalc with `suppress_alerts` delivers nothing but sets baseline
6. `all_policies` tracks two policies independently
7. deleting a policy cascades its alerts; deleting a rule keeps its history
8. SaaS SSRF guard rejects `http://`, `169.254.169.254`, `10.0.0.1`
9. tenant isolation — tenant A's recalc never reads tenant B's rules
10. delivery retry advances `attempts` and lands on `failed`

Plus the existing `templates_parse.rs` picks up the new templates for free.

## 9. Out of scope for 0.8.0

- Alerts on **systems** or **groups** (schema supports it; `scope_type` is
  already a discriminator — add `'system'` later with no migration)
- Recovery ("back to normal") notifications
- Cross-server aggregation (one OpenSCM notifying another). Dropped
  deliberately: it would need an inbound HTTP API, which is a new security
  surface for a feature nobody has asked for yet. A central collector can
  still be fed today via `webhook`.
- Alert digests / grouping
- Maintenance windows
- Per-user notification preferences
