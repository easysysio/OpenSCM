# Design — REST API, v1 (1.0.0)

**Status:** decided 2026-10-30 (recommendations accepted: freeze in 1.0.0;
`/api/v1beta1` removed in 1.1.0; `null` for "not scanned"). Steps 1–2 built.
**Target release:** 1.0.0
**Author:** Yariv + Claude (design review)

---

## 1. Goal

`/api/v1beta1` shipped in 0.12.0 (design: `0.12.0-rest-api.md`). Writing the
worked examples for `docs/guide/api.md` meant running every one against a
server with real data. That surfaced nine places where the API is awkward,
wrong against its own docs, or missing something an integration needs:

| # | What the examples showed | Where |
|---|---|---|
| 1 | Scores are unrounded: `66.66666666666666`. "Not scanned" is `-1`. | every `score` |
| 2 | Some timestamps are `2026-10-29 19:43 UTC` or `2026-10-29 19:43:00`, not ISO 8601 with `Z` as D4 promises | `/systems/{id}/compliance` `last_seen`, `/policies/{id}/compliance` `submission_date` |
| 3 | `evidence` is a JSON array packed into a string, so clients decode it twice | both compliance endpoints, saved reports |
| 4 | A result has no "checked at" time, so a CI job cannot tell a fresh result from last week's. The CI example has to `sleep` past the check-in interval. | both compliance endpoints |
| 5 | On a policy, `systems_passed`/`systems_failed` count **test results** in the default "test" compliance mode, and systems only in "system" mode | `/policies`, `/policies/{id}` |
| 6 | Audit `details` is a JSON object on some entries and plain text on others | `/audit-log` |
| 7 | Once `next_cursor` is `null` there is nothing to save, so polling "what's new since last time" needs a workaround (the SIEM example re-reads by `since` + id) | every list |
| 8 | The live policy report carries `submitter_name`/`submission_date`, meaningless on a report nobody saved | `/policies/{id}/compliance` |
| 9 | The saved-report list names the policy but not its id, so a client cannot match reports to `/policies` | `/reports/policy` |

Most come from one decision in 0.12.0 (D4): *no API-specific shape for
compliance data* — the compliance endpoints serialise the structs the pages and
PDF render from (`SystemReportData`, `ReportData`, `IndividualResult`). Those
structs hold display strings, sentinel values and stored JSON as text, which
is right for a template and wrong for an API.

All nine are cheap to fix now and impossible to fix once `/api/v1` is frozen.
1.0.0 publishes **`/api/v1`**, with them fixed, and keeps `/api/v1beta1` working
unchanged for a while (D1).

Not in scope: new endpoints or areas (users, alert rules, enrollment tokens,
editing tests). v1 covers exactly what v1beta1 covers; additions come later as
additive v1 changes.

## 2. Decisions proposed

### D1 — `/api/v1` beside `/api/v1beta1`; beta removed in 1.1.0

- 1.0.0 serves both. `/api/v1beta1` keeps today's responses **byte for byte**,
  so nothing that works against it breaks on upgrade. Its responses gain a
  `Deprecation: true` header and a `Link` to the migration section of the docs.
- 1.1.0 removes it: every `/api/v1beta1` path answers `410 Gone` with a JSON
  error pointing to `/api/v1`.
- From 1.0.0, `/api/v1` is **frozen**: fields and endpoints may be added,
  nothing is renamed, removed or changes type or meaning. A breaking change is
  `/api/v2`. The API docs page and the OpenAPI file say so.
- Same tokens, roles, rate limit, errors, audit and plan limits as v1beta1 — all
  of 0.12.0 D1, D2, D5 and D6 carry over unchanged.

The 0.12.0 design said v1 would be frozen "once a real integration has used
it". Every documented example has now been run end to end against v1beta1,
which is the closest thing available; see question 1.

### D2 — The API gets its own output types

Reverses 0.12.0 D4's last bullet. The **queries** stay shared — the API still
calls `fetch_system_report_data`, `fetch_live_policy_report_data` and so on, so
there is still one definition of how compliance is computed. What changes is
the last step: a new `api/shape.rs` turns those structs into API types
(`ApiResult`, `ApiSystemCompliance`, `ApiPolicyCompliance`, …), and every v1
handler returns those. Pages, PDFs and saved snapshots are untouched.

v1beta1 keeps calling `serde_json::to_value` on the shared structs, as today.

Field names stay as in v1beta1 except where a decision below changes them
(decided while building step 2): renaming everything (`policy_groups`,
`pass_count`, …) would break every script for little gain. One route list
serves both versions; a handler asks which prefix it was called on.

### D3 — Scores: two decimals, `null` when there is nothing to score

- Every score is a number rounded to 2 decimals (what the pages show), e.g.
  `66.67`.
- "Not scanned" (`-1` today) becomes `null`. A sentinel inside a number field
  silently corrupts an average; `null` fails loudly.
- One helper, `shape::score(f64) -> Option<f64>`, used for every score field.

### D4 — Timestamps: one format, one name pattern, enforced by a test

- Every timestamp is ISO 8601 UTC with `Z` (`2026-10-29T19:43:00Z`), produced
  by `api::iso` and nothing else.
- Every timestamp field name ends in `_at`: `last_seen_at`, `checked_at`,
  `saved_at`, `generated_at`, `created_at`, `expires_at`.
- A test fetches every GET endpoint from a seeded server, walks the JSON, and
  fails if any `*_at` value is not `^\d{4}-\d\d-\d\dT\d\d:\d\d:\d\dZ$` (or
  `null`), or any other key holds something that looks like a date. This is
  what would have caught #2.

### D5 — `evidence` is JSON, not a string

- `evidence` is the array of condition objects itself, or `null` when there is
  none (results from before 0.6.4, not scanned, excluded).
- Saved snapshots store it as text; it is parsed when served. A snapshot whose
  evidence does not parse (none known) gets `null`, never an error.

### D6 — Every result says when it was checked; runs say when they started

- Each result gains `checked_at`: `results.last_updated`, the time the server
  received the agent's verdict. `null` for "not scanned".
- `POST /policies/{id}/run` returns `202` with `queued_at` and the systems the
  run reached:
  `{"policy_id": 3, "queued_at": "…Z", "systems": [{"id": 7, "name": "web1", "online": true}, …]}`.
- A CI job then waits for every result on its system to have
  `checked_at >= queued_at` — no guessing at check-in intervals. The CI example
  in the docs is rewritten this way, with a timeout for an offline agent.
- Saved snapshots have no `checked_at` (it was never stored); in saved reports
  the field is absent rather than `null`, and the docs say so.

### D7 — Policy counts say what they count

- A policy carries both, whatever the compliance mode:
  `"systems": {"passed": 4, "failed": 1}` (fully compliant / with at least one
  failure) and `"tests": {"passed": 52, "failed": 3}` (results), plus
  `"score"` (the mode's score), `"scoring_mode": "test" | "system"`, and the
  three per-axis scores as today (`score_by_test`, `score_by_system`,
  `score_by_container`).
- The `policies` columns `systems_passed`/`systems_failed` stay as they are —
  the pages show them under a generic Pass/Fail header and rely on the
  mode-dependent meaning. Schema v51 adds `tests_passed`, `tests_failed`,
  `compliant_systems`, `failing_systems`, filled by the same
  `update_policy_stats` statement regardless of mode, so the API reads columns
  instead of re-aggregating per request.
- Tests' `systems_passed`/`systems_failed` already count systems; in v1 they
  become `"systems": {"passed", "failed"}` too, for one shape everywhere.

### D8 — Audit `details` is always an object

- An object, or `null`. Entries written as plain text are served as
  `{"message": "…"}`.
- Separately, the remaining call sites that write text details move to objects,
  so new entries are structured at the source. The read-side wrapping stays for
  old entries.

### D9 — Every list returns a resume point

- Lists return `{"data": [...], "next_cursor": "…" | null, "resume_cursor": "…"}`.
- `next_cursor` is unchanged: present while more pages exist.
- `resume_cursor` is always present: the cursor after the last row returned,
  or the request's own cursor when the page is empty. Save it, pass it as
  `?cursor=` next time, and get only what was added since. The SIEM example
  shrinks to "store `resume_cursor`, loop".
- Cursors stay opaque and id-based (0.12.0 D4); ids only grow, so this is exact.

### D10 — Report fixes

- **Live policy report** (`/policies/{id}/compliance`): drops `submitter_name`
  and `submission_date`; gains `generated_at` (now). Systems carry their `id`
  as well as their name, and each result its `test_id`, so a client can act
  on a finding (exclude it, open the system) without a name lookup.
- **Saved policy reports** gain the policy's id: schema v51 adds
  `reports.policy_id` (nullable). New saves fill it; old rows are backfilled
  where exactly one policy in the organization has that name, and stay `null`
  otherwise (the policy may since have been renamed or deleted). The list
  item becomes `"policy": {"id": 3 | null, "name", "version"}`.
- Saved-report bodies go through the same shaping as live ones (D3–D5), so a
  saved and a live report of the same policy have the same shape, minus
  `checked_at`.

### D11 — Docs and OpenAPI

- `docs/api/openapi.yaml` describes `/api/v1`. The v1beta1 spec moves to
  `docs/api/openapi-v1beta1.yaml`, unchanged, until 1.1.0. The drift test
  checks both against the router.
- `docs/guide/api.md` switches every example to `/api/v1`, adds a short
  **"Moving from v1beta1"** table (one row per change above), and states the
  stability promise from D1. Every example is re-run against the demo server
  before the commit, as this time.
- CHANGELOG: one entry listing the v1 changes and the v1beta1 deprecation.

## 3. Build order

1. Schema v51 (`policies` count columns, `reports.policy_id` + backfill);
   `update_policy_stats` fills the new columns; saving a policy report fills
   `policy_id`.
2. `api/shape.rs` and the `/api/v1` router. v1beta1 handlers stay as they are;
   v1 handlers are the same queries plus shaping. Deprecation headers on
   v1beta1. The D4 shape test, plus tests for D3, D5–D10.
3. Audit call sites that still write text details (D8).
4. OpenAPI split, docs page, examples re-run (D11).

1.0.0 also carries backup and restore (already built and released in 0.13.0)
and the stability work on the roadmap; v1 is one item of it.

## 4. Questions for review (answered 2026-10-30)

1. **Freeze now?** Freeze `/api/v1` in 1.0.0 on the strength of the examples
   (recommended) — or ship it as `v1` but frozen only from 1.1.0, giving one
   release for a real integration to find what the examples did not?
2. **Beta lifetime (D1):** remove `/api/v1beta1` in 1.1.0 (recommended), or
   keep it through all of 1.x?
3. **`null` for "not scanned" (D3):** agreed, or keep `-1` for continuity with
   the pages and exports?
