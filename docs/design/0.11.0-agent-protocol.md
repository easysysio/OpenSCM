# Design — agent protocol decisions before 1.0

**Status:** decided 2026-10-18. D1, D2 and D4's agent-side checks shipped in
0.10.4; D3, D5 and D6 are built for 0.11.0 (§6 has the details as built);
release signing (D4b) is its own piece of work.
**Author:** Yariv + Claude (design review)
**Last updated:** 2026-10-18

---

## 1. Why now

1.0 is a promise about the protocol between the server and the agents more
than about anything else: agents stay deployed for years, on hosts nobody
logs in to, and every later server has to keep talking to them. Whatever is
wrong in the protocol at 1.0 is wrong for a long time.

## 2. How it works today

Each agent has its own Ed25519 key pair per server URL and signs every
heartbeat (`POST /send`) and every result (`POST /result`). The server signs
every reply with the organization's active key from `tenant_keys`, and the
agent checks the reply against the server key it saved at registration
(`server_<namespace>.pub`).

## 3. What is wrong with it

1. **The agent gives up the server's key on demand.** A reply with a bad
   signature, or an HTTP 404, makes the agent delete the saved server key.
   With no key saved, the next reply is not checked at all, and the key it
   carries is saved. That unchecked reply can be an UPGRADE naming any URL
   and hash, which the agent downloads and runs, whatever `cmd_enabled` says.
   Anyone who can sit between the agent and the server (plain HTTP, DNS
   spoofing) can therefore run code as root on the host in two replies.
   Signing-key rotation relies on exactly this: agents drop the old key and
   trust whatever comes next.
2. **No freshness or binding.** The heartbeat's timestamp is never checked,
   and a reply is not tied to the request it answers. Old TEST replies
   (including CMD tests since removed), old UPGRADE replies (a downgrade) and
   old PASS results can all be replayed.
3. **The server holds root on the fleet through UPGRADE.** Agent binaries are
   trusted only by a hash the server itself sends.
4. **No protocol version.** Compatibility rests on new fields being optional;
   there is no way to say "this agent is too old".
5. Registration does not prove possession of the presented key and is not
   rate-limited. Results go one per request.

## 4. Decisions

### D1 — The agent pins the server's key

The key saved at registration is kept. A reply with a bad signature is
refused and logged, never treated as a reason to drop the key. A 404 resets
the agent's ID (the system was deleted on the server) but not the key.
With no key saved, the agent acts on nothing but the registration reply.

A new key is trusted only through D2, or by someone on the host running
`scmclient --reset-server-key`. A server that is reinstalled with a new key
therefore needs that command on each host; that is the price of not letting
anyone on the network do it instead.

### D2 — Rotation without trusting blindly

Rotate Signing Key creates a new key, and the old one keeps signing for a
**30-day grace period** (`tenant_keys.retire_after`).

Each heartbeat names the server key the agent holds (`server_key`). The server
signs with that key while it is within its grace period, and the reply
announces the new one (`next_server_public_key`). The agent switches only
because a reply signed by the key it already trusts told it to. The server
records the key each agent reports (`systems.agent_server_key`), so the
Danger Zone can show how many agents have switched.

An agent that is off for the whole grace period needs the manual reset.

Agents from before this change send no `server_key`; they are signed for
with the active key and re-trust as they always have, so they keep working.

### D3 — Freshness and binding (0.11.0)

Requests carry a random nonce that the server repeats inside the signed
reply; the agent rejects a reply that does not carry its nonce. The server
rejects a request whose timestamp is more than 5 minutes off, or not newer
than the last it accepted from that agent (one column per system). Results
get the same timestamp.

### D4 — UPGRADE is locked down

The agent downloads an upgrade only from its own server (a relative path, or
the same scheme, host and port as its configured URL), and never to a version
that is not newer than its own.

**D4b, separate work:** the build host signs agent binaries with a release
key built into the agent, which checks the signature before installing. Then
even a compromised server cannot push its own binary.

### D5 — Explicit protocol version (0.11.0)

Requests and replies carry `protocol: 1`. Adding optional fields keeps the
number; anything that breaks old agents raises it. A server refuses
unsupported versions with a clear message in the Systems list. A 1.x server
keeps accepting today's 0.x agents on their old terms, shown as *legacy
protocol*, so the fleet can be upgraded.

### D6 — Registration checks (0.11.0)

The registering agent signs its payload with the key it presents, and the
server checks it. Registrations are rate-limited per client address
(`rate_limit.rs`).

### Not before 1.0

Batched results, and requiring HTTPS. With D1–D3 signatures protect the
messages even over plain HTTP, but not their privacy; agents on HTTP get a
warning in the Systems list rather than refusal.

## 5. The limit

Agents already deployed keep problem 1 until they run an agent with D1, and
reaching them goes through the very UPGRADE path that is weak. Ship D1 soon
and upgrade the fleet promptly.

## 6. D3, D5 and D6 as built (0.11.0)

**Wire fields (protocol 1).** Heartbeats carry `protocol: 1`, a random 128-bit
`nonce` and `sent_at_ms`; results carry `protocol` and `sent_at_ms`. The agent
keeps one clock for both (`next_sent_at_ms`): wall-clock milliseconds, but
always later than the previous value, so two results in one millisecond or an
NTP step backwards never produce an older time.

**Server checks**, after the signature is verified (`client::claim_request`):
`sent_at_ms` within 5 minutes of the server's clock, and greater than
`systems.last_request_ts`; the comparison and the update are one statement.
`systems.agent_protocol` records the highest version seen. A request with no
`protocol` is accepted on the old terms only while that is NULL; afterwards it
can only be a recording, and is refused. A version above 1 is refused with a
message naming the server's version. Refusals are unsigned JSON
`{"error": …}`, which the agent now logs.

**Reply binding.** A reply to a protocol-1 request carries `protocol` and the
request's `nonce` inside the signed payload. The agent refuses a reply whose
nonce is not its own. Once it has seen its server reply with a protocol (on a
reply verified with the pinned key), it records that
(`server_<namespace>.protocol`) and from then on refuses replies without one,
so a recorded pre-upgrade reply cannot be replayed to it.
`--reset-server-key` forgets this too.

**Registration.** Every registration must carry a public key and be signed by
it — agents have always signed it; the server never checked. A protocol-1
registration must also be within the clock window. Registrations that land in
the pending queue (no valid enrollment token) are limited to 100 an hour per
client address (`rate_limit::REGISTER_PENDING`).

**Visibility.** Active systems whose agent has never spoken protocol 1 show a
*legacy protocol* badge in the Systems list.

**Schema** v45 → v46: `systems.last_request_ts`, `systems.agent_protocol`.

**Not covered:** a heartbeat from before protocol 1 that an attacker recorded
can still be replayed against a system whose agent has never been upgraded —
the server has no way to tell it apart. Upgrading the agent closes it.
