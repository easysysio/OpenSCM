# Design — Guided First Run (0.8.0)

**Status:** approved, implementation pending
**Target release:** 0.8.0
**Author:** Yariv + Claude (design review)
**Last updated:** 2026-08-20

---

## 1. Goal

A fresh OpenSCM install shows an empty dashboard: 0 systems, 0 policies, 0%
compliance. Everything the product does is real, and none of it is visible
until the operator has independently worked out that the order is
*agent → test → policy → run*. Nothing on screen says so.

Add a short guided walkthrough on first login that names the four steps and
links into each one, with a **"Don't show this again"** checkbox.

Decisions locked with the user:

1. **Multi-screen** — a few screens, not one wall of text.
2. **Covers** registering a system, creating a test, creating a policy,
   running it.
3. **Dismissible** with a "don't show again" checkbox.

---

## 2. When it appears

Three conditions, all required:

1. The current user has `tour_done = 0`
2. The request is for the **dashboard** (`/`) — not any other page
3. The user's role can act on the content (§6)

Restricting to the dashboard is deliberate. A modal that can appear over any
page will eventually appear over a half-completed form. The dashboard is the
one page where interrupting costs the user nothing, and it is where they land
after login anyway.

The tour is **not** gated on "zero systems". An operator who registered one
host and then got lost still needs steps 2–4, and the dismissal flag already
means it disappears the moment it is unwanted.

---

## 3. Data model

Schema **v37 → v38**.

```sql
ALTER TABLE users ADD COLUMN tour_done INTEGER NOT NULL DEFAULT 0;
UPDATE users SET tour_done = 1;      -- existing users are not new users
```

That second statement is the whole subtlety of this migration. Without it,
every operator who has been running OpenSCM for months gets a "welcome, let's
register your first system" modal on their next login after upgrading. The
column defaults to 0 so genuinely new users still see it; the one-time UPDATE
excludes everyone who predates the feature.

### 3.1 Why a database column, not localStorage

Per-user in the database, because this is a user preference, not a browser
preference. `localStorage` would re-show the tour when the same person opens
OpenSCM from a second machine or a private window, and would suppress it for a
brand-new colleague sharing a workstation. Both are wrong in the annoying
direction.

One column on `users` rather than a preferences table: there is exactly one
flag, it is queried on every dashboard render, and the existing `AuthSession`
lookup can carry it at no extra cost. A generalised preferences table can come
later if a second flag ever appears.

## 4. The screens

Five panes in one modal, previous/next, progress dots, `Esc` closes. Each
content pane is a short paragraph, a diagram or annotated screenshot, and a
button that navigates to the real page.

### Screen 1 — Welcome

> **Welcome to OpenSCM.**
> OpenSCM checks your machines against rules you define and scores how many
> pass. Four steps to your first compliance report — about ten minutes.
>
> `[1] Register a system → [2] Write a test → [3] Group into a policy → [4] Run it`

Naming the shape of the whole workflow up front is the single highest-value
screen. The four-box diagram is the mental model the product currently never
states, and it is what makes the remaining screens make sense.

### Screen 2 — Register a system

> Install the agent on a machine. It enrolls itself, reports its inventory,
> and stays connected.
>
> Install from the package repository, point the config at this server, then
> approve the system under **Systems**.
>
> ```
> sudo apt install scmclient          # after adding the OpenSCM repo
> ```
> ```toml
> # /etc/openscm/scmclient.config
> [server]
> url = "{{ server_url }}"
> organization = "default"
> ```
> `[ Enrolment tokens → ]`   `[ Systems → ]`

**The config snippet is filled in with the tenant's real server URL**, so the
one OpenSCM-specific value is not left as a placeholder to go and look up.

The token is NOT pre-filled, and cannot be: `enrollment_tokens` stores only
`token_hash`, so plaintext exists once at creation and is unrecoverable. The
alternative — minting a token as a side effect of *viewing* a tour — creates
credentials nobody asked for, so the screen says plainly that tokens are shown
only once.

The approval step is part of this screen rather than glossed over. An agent
that installs cleanly and then sits in Pending is the single most likely place
for a first-time operator to conclude the product is broken.

If the tenant has no active enrollment token, the tour creates one scoped to
this walkthrough (or links to `/enrollment` if the user's role cannot).

### Screen 3 — Create a test

> A **test** is one check: a file permission, a running service, a sysctl
> value, the output of a command. Each test has elements and conditions that
> decide PASS, FAIL, or N/A.
>
> Start from the **Policy Store** for ready-made CIS-style content, or write
> your own.
>
> `[ Browse the Policy Store → ]`   `[ Create a test → ]`

Pointing at the Policy Store first is intentional — importing a curated policy
is a far better first experience than authoring conditions from scratch, and
it is a feature operators frequently never discover.

### Screen 4 — Build a policy

> A **policy** is a set of tests applied to a set of systems or groups. The
> policy is what gets scored, scheduled, and reported on.
>
> `[ Create a policy → ]`

### Screen 5 — Run it and watch

> Run the policy now, or put it on a schedule. Results land in the compliance
> report and build a trend over time.
>
> `[ Go to Policies → ]`   `[ View the dashboard → ]`
>
> `[x] Don't show this again`        `[ Finish ]`

When alerting lands in 0.9.0 this screen gains a `[ Set up an alert → ]`
button, so the tour ends by pointing at the thing that means the user never
has to come back and look manually. Until then it closes on the dashboard.

### 4.1 The checkbox

"Don't show this again" sits on the **last** screen, checked by default, and
`Finish` is the primary button. Someone who has read all five screens does not
need them again. Closing early with `Esc` or the X does **not** set the flag —
an accidental dismissal on screen 2 should not permanently destroy the tour.

---

## 5. Reopening it

A **Quick start** item in the user dropdown (next to Support) reopens the tour
at screen 1 without clearing `tour_done`. Dismissal must never be a one-way
door: the operator who clicked through it in a hurry on day one is exactly the
person who wants it back on day three.

---

## 6. Role adaptation

A Viewer cannot create tests or policies and cannot install agents. Showing
them four screens of buttons they will be denied at is worse than showing
nothing.

| Role   | Behaviour                                                     |
|--------|---------------------------------------------------------------|
| Viewer | Tour suppressed; `tour_done` left at 0 so a later promotion shows it |
| Runner | Screens 1, 4, 5 — no authoring steps, run/schedule emphasised  |
| Editor | All five, minus the enrollment-token management link           |
| Admin+ | All five                                                       |

Leaving `tour_done = 0` for Viewers rather than setting it is the detail that
matters: promoting a Viewer to Editor six months later then surfaces the tour
at the moment it first becomes relevant.

---

## 7. Implementation

- `scmserver/templates/partials/tour.html` — the modal, included from
  `base.html` under `{% if show_tour %}`
- `show_tour` computed in the dashboard handler only
- Content is static markup; no new JS dependency. AdminLTE's Bootstrap modal
  plus ~40 lines of vanilla JS for pane switching
- Diagrams are inline SVG, theme-aware, no image assets to ship
- `POST /tour/dismiss` → `UPDATE users SET tour_done = 1 WHERE id = ?`,
  returns 204; the modal closes optimistically
- `GET /tour/reopen` → renders the dashboard with `show_tour = true`

### Routes

| Method | Path            | Role   | Purpose                       |
|--------|-----------------|--------|-------------------------------|
| POST   | `/tour/dismiss` | Viewer | Set `tour_done = 1`           |
| GET    | `/tour/reopen`  | Viewer | Show the tour again           |

---

## 8. SaaS differences

The SaaS build overrides screen 2: there is no `--server` to choose, and the
install snippet uses the tenant's assigned endpoint. A SaaS tenant also
reaches the tour at a different moment — immediately after email verification
rather than after a fresh install — so the SaaS dashboard handler sets
`show_tour` on first login post-verification.

Everything else is shared. The template takes the install snippet as a
variable rather than branching on `saas_mode` internally.

---

## 9. Test plan

New `scmserver/tests/first_run.rs`:

1. Migration sets `tour_done = 1` for pre-existing users, 0 for new ones
2. `show_tour` true on `/` for a new Admin, false on `/systems`
3. `POST /tour/dismiss` flips the flag; second dashboard load has no tour
4. Viewer never sees the tour and the flag stays 0
5. Promoting that Viewer to Editor surfaces the tour
6. The rendered snippet contains a real token, not the literal `{{ token }}`
7. `templates_parse.rs` covers the new partial

## 10. Out of scope for 0.8.0

- Per-feature contextual tips
- Video content
