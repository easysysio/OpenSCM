# Design — SaaS single sign-on (0.10.0)

**Status:** in progress — provider configuration built (step 1 of 3); sign-in next
**Target release:** 0.10.0
**Author:** Yariv + Claude (design review)
**Last updated:** 2026-10-10

---

## 1. Goal

CE authenticates against a customer's LDAP. SaaS cannot: the server has no route
into a customer's internal network, which `directories.rs` states outright —

> LDAP is intentionally disabled in SaaS mode … Use OIDC/SAML SSO (task #3) for
> SaaS-side identity federation instead.

So a SaaS customer provisions and deprovisions every user by hand, in OpenSCM,
separately from their own directory. That fails the offboarding question in
every enterprise security review, and it is asked early.

Decisions locked with the user:

1. **OIDC only.** Covers Entra ID, Google Workspace, Okta, Auth0 and Keycloak.
   SAML is XML signature verification — canonicalisation, key resolution, replay
   defence — with no comparable Rust crate; a mistake there is an authentication
   bypass. Add it when a customer refuses to proceed without it, not before.
2. **No just-in-time provisioning.** SSO *authenticates*; it does not create
   accounts. Someone who authenticates successfully but has no OpenSCM user is
   refused, with a message saying so.
3. **Password login keeps working.** SSO becomes the normal path, but a
   misconfigured issuer or an expired client secret must not lock a tenant out
   of its own account.

Two decisions revised on 2026-10-06, before implementation:

4. **The sign-in page finds the provider by Organization, not by email
   domain.** The first draft had each tenant list its email domains. Nothing
   stops a tenant listing a domain it does not own, and then another company's
   users, typing their address, are sent to a stranger's "identity provider"
   page — a ready-made phishing route. Preventing that means verifying domain
   ownership, a feature in itself. Since 0.9.4 the SaaS sign-in form requires
   the Organization anyway, so the user names their organization and chooses
   "Sign in with SSO". No domain list, nothing to claim. In CE, with its single
   organization, it is simply a button when a provider is enabled.
5. **ID tokens are verified with `jsonwebtoken` (on `ring`), and the flow
   around it is written here.** The first draft used the `openidconnect` crate.
   Measured against this codebase it adds 37 crates, among them `rsa` — the
   crate under RUSTSEC-2023-0071 that both repos' audit configuration ignores
   on the stated ground that it is never compiled. `jsonwebtoken` adds one
   crate and uses the crypto provider already in the build. The signature and
   claim checks (§4.1) stay in a maintained library; discovery, PKCE, state,
   nonce and the code exchange are ours, and every check in §4.1 has a test
   that shows it rejecting.

Decided on 2026-10-10:

6. **SaaS only in 0.10.0.** The code lives in the crate both editions share,
   so the first build of the configuration page worked in Community Edition
   too — by accident of where the code is, not because CE needed it. CE has
   LDAP. Offering SSO there would mean a second sign-in page variant, a second
   set of URL rules to keep correct (internal addresses, plain http), and
   supporting self-hosted setups that vary far more than SaaS does.

   The two choices are not symmetric. Opening SSO to CE later is small: remove
   the gate (`sso::unavailable`) and add the CE sign-in button. Withdrawing it
   after CE users have configured it is not really possible. So it starts
   closed. In CE every SSO route redirects with "not available in this
   edition", for administrators too, the mirror image of how LDAP directories
   are closed in SaaS. The tables are created in both editions (one schema);
   in CE they stay empty.

   What CE would gain, for when this is revisited: sign-in for organizations
   whose directory is cloud-only (Entra ID, Google Workspace, Okta — no LDAP
   server), and the provider's multi-factor authentication, which OpenSCM does
   not have of its own.

## 2. Why not reuse the `directories` table

`directories` is LDAP-shaped: `host`, `port`, `base_dn`, `bind_dn`,
`bind_password`, `user_attribute`, all `NOT NULL`. An OIDC provider has none of
those and needs an issuer URL, client ID and secret instead. Reusing the table
means five columns carrying `''` to satisfy constraints that describe a
different protocol, and a `dir_type` discriminator that every query must respect
or silently mix the two.

A separate table is smaller than the confusion it avoids.

## 3. Data model

Schema **v42 → v43** (v42 was taken by revocable sessions in 0.9.4).

```sql
CREATE TABLE IF NOT EXISTS sso_providers (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    tenant_id      VARCHAR(191) NOT NULL,
    enabled        INTEGER NOT NULL DEFAULT 0,
    name           TEXT NOT NULL,          -- "Acme Entra ID", shown on the button
    issuer_url     TEXT NOT NULL,          -- discovery root, no trailing slash
    client_id      TEXT NOT NULL,
    client_secret  TEXT NOT NULL,
    created_at     DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at     DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (tenant_id),
    FOREIGN KEY (tenant_id) REFERENCES tenants (id) ON DELETE CASCADE
);
```

One provider per tenant. Multiple providers per tenant is a real ask eventually
(a company with two IdPs mid-merger) but it doubles the routing logic for a case
nobody has yet.

```sql
ALTER TABLE users ADD COLUMN sso_subject TEXT;
CREATE UNIQUE INDEX idx_users_sso ON users (tenant_id, sso_subject)
    WHERE sso_subject IS NOT NULL;
```

`sso_subject` is the IdP's `sub` claim — the only identifier an IdP guarantees
stable. Email addresses change; `sub` does not.

### 3.1 Transient login state

```sql
CREATE TABLE IF NOT EXISTS sso_login_state (
    state         TEXT PRIMARY KEY,
    tenant_id     VARCHAR(191) NOT NULL,
    nonce         TEXT NOT NULL,
    pkce_verifier TEXT NOT NULL,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

Server-side rather than in a cookie so the values cannot be read or replayed by
anything that can see the browser's storage. Rows are single-use, deleted on
callback, and anything older than 10 minutes is swept by the existing retention
task — an abandoned login must not leave a usable state token lying around.

## 4. The flow

```
  /login  ── organization ──►  that tenant's enabled provider
                                                          │
                                    redirect with state, nonce, PKCE
                                                          ▼
                                                   customer's IdP
                                                          │
  session  ◄── user matched ◄── ID token validated ◄── /auth/sso/callback
```

1. **`POST /auth/sso/start`** — takes the organization (decision 4; in CE
   there is only one) and finds its enabled provider. An organization with no
   enabled provider gets the same answer as one that does not exist.
2. Generates `state`, `nonce` and a PKCE verifier, stores them, and redirects to
   the provider's authorization endpoint (discovered from
   `issuer_url/.well-known/openid-configuration`).
3. **`GET /auth/sso/callback`** — exchanges the code, validates the ID token,
   and resolves the user.

### 4.1 Validation, in order

Every one of these is load-bearing; the whole security of the flow is here.

| Check | Why |
|---|---|
| `state` exists and is unused | CSRF on the callback |
| `nonce` matches the ID token claim | token replay |
| PKCE verifier matches | authorization-code interception |
| Signature verifies against the issuer's JWKS | forged tokens |
| `iss` equals the configured issuer exactly | a different IdP's valid token |
| `aud` contains our `client_id` | a token minted for another application |
| `exp` in the future, `iat` not far in the past | stale tokens |

Signature, `iss`, `aud` and `exp` are checked by `jsonwebtoken`; state, nonce
and PKCE by code in this repository (decision 5). Getting this list wrong is an
authentication bypass, not a bug, so each row has a test in which a token or
callback that violates it is refused.

A session created this way is issued by `auth::issue_session_cookie`, the same
as a password login, so it carries the same expiry and is subject to the same
per-request checks (user still exists, organization not suspended, session
epoch). A verified email from the provider also counts as the user's email
verification, or a SaaS user who never clicked their confirmation link would
sign in and be turned away by that check.

### 4.2 Resolving the user

```
sub matches users.sso_subject in this tenant   →  that user
else email matches a user in this tenant       →  bind sub to them, then that user
else                                           →  REFUSE
```

Binding on first login is what lets an existing account become an SSO account
without an admin touching it. The refusal is deliberate (decision 2): the IdP
says who someone *is*, never that they should have access.

**Email matching requires `email_verified: true` from the IdP.** Without that,
an IdP where users can set their own unverified address lets someone claim
another user's account by typing their email. Providers that omit the claim are
treated as not verified.

Matching is always scoped to the provider's tenant. A `sub` from Acme's IdP can
never resolve to a user in Globex, whatever it claims.

### 4.3 Users who cannot sign in this way

A user with `sso_subject` set may still use their password — decision 3, the
break-glass path. What SSO does not do is create, promote or disable anyone.
Deprovisioning still means disabling the OpenSCM account; removing someone from
the IdP stops them authenticating *through it*, which is most of the value, but
the docs must say plainly that it is not a full deprovision.

## 5. SSRF containment

`issuer_url` is supplied by a tenant, and the server fetches it — discovery,
JWKS and the token endpoint are all outbound requests to an address a customer
chose. That is the same exposure as alert webhooks, and gets the same treatment:
the rules moved from `alert_delivery` into `net_guard` (`check_url`,
`client_for`), shared by both.

In SaaS: `https` only, and the resolved address must not be loopback,
link-local, private, unspecified or carrier-grade NAT — checked when the
provider is saved **and** before each outbound request, because DNS can be
re-pointed in between. The request is made by a client pinned to the addresses
that passed the check, so the name cannot be re-pointed between the check and
the request either. Redirects are disabled. The endpoints a discovery document
lists are held to the same rules, and the document must name the issuer it was
fetched from.

Since SSO is SaaS-only (decision 6), the strict rules always apply in practice.
The strictness is still a parameter of the functions that do the work
(`save_provider`, `test_provider`, `discover`) rather than read from the
edition inside them: the routes pass "strict", and the tests pass "relaxed" to
exercise the logic against a provider on a local port. The relaxed rules are
also what a self-hosted deployment would need to federate with an internal
Keycloak, if SSO is opened to CE later.

## 6. Routes

All SaaS only (decision 6).

| Method | Path | Role | Purpose |
|---|---|---|---|
| POST | `/auth/sso/start` | — | Begin, given the organization |
| GET | `/auth/sso/callback` | — | Complete, create the session |
| GET | `/admin/sso` | Admin | Configure the tenant's provider |
| POST | `/admin/sso/save` | Admin | Save |
| POST | `/admin/sso/test` | Admin | Fetch discovery, report what was found |
| POST | `/admin/sso/disable` | Admin | Turn it off |

`/admin/sso/test` matters for the same reason the alert **Send test** button
does: a wrong issuer URL or client secret is otherwise invisible until a user
cannot log in, and that user is not the person who typed it.

The client secret is never rendered back into the page — the form shows
"unchanged" and a blank submission keeps the stored value, exactly as the alert
webhook secret does.

## 7. Test plan

`scmserver/tests/sso.rs`:

1. The organization selects that tenant's provider; an organization without
   an enabled provider and one that does not exist are indistinguishable
2. A valid ID token for a known `sub` produces a session for that user
3. First login binds `sub` to a user matched by verified email
4. `email_verified: false` (or absent) refuses to match by email
5. A successful token for an unknown user is REFUSED, and no account is created
6. A `sub` from tenant A never resolves to a user in tenant B
7. Wrong `aud`, wrong `iss`, expired `exp`, bad signature — each rejected
8. A replayed `state` is rejected; state rows are single-use
9. A mismatched `nonce` is rejected
10. SaaS refuses an issuer URL resolving to a private address, at save and at use
11. The stored client secret is never present in a rendered page

## 8. Out of scope for 0.10.0

- **SAML** — until a customer requires it
- **Just-in-time provisioning** and **group-to-role mapping** — decision 2;
  both are additive later without schema change beyond a column
- **SCIM** provisioning/deprovisioning — the real answer to offboarding, and a
  project of its own
- **Multiple providers per tenant**
- **IdP-initiated login** — the "click the tile in Okta" flow, which needs its
  own replay handling
