# Design — Network device compliance (2.0.0)

**Status:** draft for review (2026-10-28)
**Target release:** 2.0.0 (phase 1 vendors); 2.1.x (phase 2 vendors)
**Author:** Yariv + Claude (design review)

---

## 1. Goal

OpenSCM checks hosts that run its agent. Switches, routers and firewalls cannot
run an agent, yet they are where many audit findings live: telnet left on,
SNMP `public`, no AAA, no logging, weak SSH. Customers who buy OpenSCM for CIS
and NIST evidence ask for the same evidence for their network.

2.0.0 lets OpenSCM check network devices **without installing anything on
them**, with the same tests, policies, reports, alerts and API as hosts.

It is a major version because it changes what a "system" is: until now every
system was an agent. From 2.0.0 a system is either an **agent host** or a
**network device** checked through one.

Out of scope for 2.0.0: changing device configuration (remediation stays
host-only), configuration backup and diffing, SNMP, auto-discovery of devices.

## 2. Decisions proposed

### D1 — Devices are reached through a collector, never from the server

The existing agent gets a **collector mode**. A collector is an ordinary agent
on a host inside the customer's network (enrolled, approved, pinned and signed
like any other agent) that additionally logs in to network devices over SSH,
runs read-only commands, evaluates tests and reports the results.

Why not let the server connect directly:

- **SaaS cannot reach customer networks** — the same reason LDAP is CE-only.
  A collector works identically for CE and SaaS.
- **Device credentials never reach the server** (D3).
- It reuses everything the agent protocol already has: enrollment tokens,
  approval, server key pinning and rotation, replay protection, signed
  results, upgrades, the commands queue.

A collector still checks its own host as usual. A customer can run several
collectors (per site, per security zone); each device is assigned to one.

### D2 — A device is a full system

Containers are stored as children of their host (`containers` table, results
tagged with `container_id`). Devices are **not** done that way: a device gets a
row in `systems`, so it joins groups and auto groups, is linked to policies,
appears in reports, PDFs, trends, alerts and the REST API, and counts toward
plan limits — with no special cases in any of those.

- New column `systems.kind`: `agent` (every existing row) or `device`.
- New table `devices`, one row per device system:

```sql
CREATE TABLE devices (
  system_id          INTEGER PRIMARY KEY,      -- FK → systems.id, CASCADE
  tenant_id          TEXT    NOT NULL,
  collector_id       INTEGER NOT NULL,         -- FK → systems.id (kind agent)
  address            TEXT    NOT NULL,         -- IP or DNS name
  port               INTEGER NOT NULL DEFAULT 22,
  driver             TEXT    NOT NULL,         -- 'cisco_ios' | 'arista_eos' | 'juniper_junos' | …
  credential_profile TEXT    NOT NULL,         -- name of a profile on the collector (D3)
  ssh_host_key       TEXT,                     -- pinned on first contact (D5)
  poll_status        TEXT,                     -- 'ok' | 'unreachable' | 'auth_failed' | 'host_key_changed' | 'not_allowed'
  poll_error         TEXT,
  last_poll_at       DATETIME,
  vendor TEXT, model TEXT, serial TEXT, os_version TEXT,   -- facts (D6)
  FOREIGN KEY (system_id)    REFERENCES systems(id) ON DELETE CASCADE,
  FOREIGN KEY (collector_id) REFERENCES systems(id) ON DELETE RESTRICT
);
```

- For a device, `systems.name` is the device name, `ip` its address, `os` the
  driver plus OS version (`cisco-ios 17.9.4`), `ver` / `protocol` / telemetry
  stay empty. The Systems page shows a **device** badge and "via *collector*";
  upgrade, telemetry and approve controls are hidden for devices.
- Deleting a collector that still has devices is refused; its devices must be
  moved to another collector or deleted first.

### D3 — Credentials stay on the collector, in named profiles

Device inventory (name, address, driver, collector) is managed in the web UI.
**Secrets are not.** The UI only names a **credential profile**; the profile
itself lives in the collector's config file:

```toml
[collector]
enabled = true
max_parallel = 8            # devices polled at once
command_timeout_secs = 30

[collector.profiles.core-switches]
username        = "oscm-ro"
key_file        = "/etc/scmclient/keys/core-switches"   # preferred
# password      = "…"                                    # if keys are not possible
# enable_secret = "…"                                    # Cisco, if the user lands below privilege 15
allowed_networks = ["10.20.0.0/16", "10.21.0.0/16"]      # required
```

- The config file is readable by the agent's account only, as today.
- A SaaS customer never hands device passwords to us, and a database or
  backup leak on the server exposes no network credentials.
- `allowed_networks` is **required** per profile. The collector refuses to
  use a profile for any address outside it (`poll_status = not_allowed`) and
  resolves DNS names before checking. This is the defence against a server
  side attacker — or a compromised SaaS server — adding a "device" at an
  address they control to capture a password: the server can name a profile
  but cannot widen where it is used.
- Key authentication is recommended in the docs; with keys, even a device
  inside the allowed networks that is impersonated learns nothing reusable.

### D4 — Read-only by construction

- The collector only ever sends commands from two sources: its driver's own
  fixed commands (disable paging, read the running config, read facts) and
  the input of **SHOW** test conditions.
- A SHOW input must start with the driver's read verb (`show` on Cisco,
  Arista and Junos; `show` / `get` on FortiOS) and may contain no newline,
  `;` or control characters. Pipes are allowed only to the driver's
  output filters (`| include`, `| exclude`, `| section`, `| begin`,
  `| count`, Junos `| match`, `| display set`). Anything else is NA with the
  reason in the evidence.
- The collector never enters configuration mode in 2.0.0.
- The docs give a least-privilege read-only account per vendor.

### D5 — SSH host keys pinned per device

Same model as agents pinning the server key (0.11.0, D1): the collector
records the device's SSH host key on first contact and sends it to the
server, which stores it in `devices.ssh_host_key`. On every later poll the
collector is told the expected key and refuses a different one
(`host_key_changed`). An Editor clears the pin from the device page after
checking the change was expected (a re-imaged device), and the clear is
audited.

### D6 — How polling works

- The collector's heartbeat reply lists its devices (id, address, port,
  driver, profile, pinned host key) and any queued test commands for them,
  from the same `commands` table, keyed by the device's system id.
- Per device and per poll the collector opens **one** SSH session, reads the
  running config once, runs each distinct SHOW command once, and evaluates
  every queued test against that snapshot. 50 tests cost one login.
- Facts and reachability are refreshed every `device_poll_minutes` (server
  setting, default 15) even with no tests queued, so a device's online status
  is current. A device is **online** when its collector is online and its
  last successful poll is within the offline threshold.
- Results are signed by the collector, with a new `device_id` field. The
  server accepts one only if that device is assigned to the signing
  collector, in the collector's organization.
- Protocol version 2 adds `collector: true` on the heartbeat and `device_id`
  on results. Protocol 1 agents are unaffected.

### D7 — New test elements

| Element | Input | Sub-elements | Notes |
|---|---|---|---|
| **CONFIG** | optional section pattern (e.g. `^interface GigabitEthernet`) | CONTENT | Running config, as lines. With a section, the condition is applied to each matching section's child lines; the test's ALL/ANY filter decides across sections. Junos is read as `display set`, so it is one flat list of lines like the others. |
| **SHOW** | a read-only command (D4) | OUTPUT | Same conditions as CMD's output. |
| **DEVICE** | — | VENDOR, MODEL, OS VERSION, SERIAL | From facts. Mostly for applicability (e.g. "only IOS-XE 17 and later"). Version compare as in the existing version conditions. |

- Existing elements on a device: HOSTNAME and IP answer from facts; OS answers
  with the driver and version; everything else (FILE, PACKAGE, SERVICE, CMD,
  REGISTRY, …) is **NA**. CONFIG, SHOW and DEVICE are NA on agent hosts. So a
  policy mixing hosts and devices simply scores each on what applies.
- **Evidence is redacted before it leaves the collector**: lines holding
  `password`, `secret`, `key`, `community`, `pre-shared` and the vendors'
  equivalents have the value replaced by `<redacted>`. The full running
  config is never sent to the server in 2.0.0.

### D8 — Drivers

One driver per vendor OS, behind one trait:

```rust
trait Driver {
    fn prepare(&mut self) -> Result<()>;          // paging off, enable if needed
    fn running_config(&mut self) -> Result<Vec<String>>;
    fn facts(&mut self) -> Result<Facts>;          // vendor, model, serial, version, hostname
    fn show(&mut self, cmd: &str) -> Result<String>;
    fn is_read_only(cmd: &str) -> bool;            // D4
}
```

| Phase | Drivers |
|---|---|
| 1 (2.0.0) | Cisco IOS / IOS-XE, Arista EOS, Juniper Junos |
| 2 (2.1.x) | Cisco NX-OS, Fortinet FortiOS, Palo Alto PAN-OS |

- SSH library: **russh** (pure Rust, tokio). The agent is cross-compiled
  with cargo-zigbuild for many targets; a C library (libssh2) would bring
  OpenSSL back into the build. Older devices need legacy algorithms
  (`diffie-hellman-group14-sha1`, `ssh-rsa`); these are offered only when a
  profile sets `legacy_algorithms = true`.
- Prompt handling and paging differ per vendor and are the main source of
  bugs in tools like this, so every driver is tested against recorded
  sessions (§4).

### D9 — Managing devices

- **Systems → Network devices → Add device**: name, address, port, driver,
  collector, credential profile. **Admin** only, like auto-group rules: adding
  a device makes a collector log in somewhere with stored credentials.
  (`allowed_networks` limits the damage either way; the role keeps it small.)
- **Test connection** button: the collector polls the device on its next
  heartbeat and the page shows the result (reachable, facts, host key).
- **CSV import** for many devices at once, with a dry-run preview.
- The collector's profile names are reported on its heartbeat (names only),
  so the form offers a list instead of free text.
- REST API v1beta1 gains `GET/POST /devices`, `GET/PUT/DELETE /devices/{id}`.
  Devices also appear in `/systems` with `kind: "device"`.
- Audit: `device.create`, `device.update`, `device.delete`,
  `device.host_key_clear`.

### D10 — Policies

The Policy Store gets CIS Cisco IOS 17, Arista EOS and Juniper Junos
benchmarks (only the automatable controls), built from CONFIG, SHOW and
DEVICE. They ship with 2.0.0, in `OpenSCM-Store`.

### D11 — Plans and editions

- CE: no limit, as for hosts.
- SaaS: a device counts as one system toward the plan's limit (see question 5).
- Collector mode is in the agent for every platform the agent already
  supports; the docs recommend Linux.

## 3. Build order

Each step ships tested and behind the collector being enabled in its config.

1. **Schema and collector skeleton**: `systems.kind`, `devices`, protocol 2,
   the device pages (add, edit, delete, move), Cisco IOS driver, reachability,
   facts, host-key pinning, `allowed_networks`, DEVICE element.
2. **Compliance on devices**: CONFIG and SHOW elements, the read-only check,
   evidence redaction, results through policies, reports, PDFs and alerts.
3. **More vendors and scale**: Arista EOS and Junos drivers, CSV import, REST
   API endpoints, parallel polling limits.
4. **Content and docs**: Store policies, user guide (setup, least-privilege
   accounts per vendor, troubleshooting), 2.0.0 is cut.

## 4. Testing

- A **fake device** for tests: a small russh server that speaks each
  driver's prompts and paging and answers from recorded outputs. Every driver,
  the redaction and the read-only check run against it in CI.
- **Recorded sessions** from real devices (scrubbed) for each supported OS
  version, kept as test fixtures.
- Lab checks before release on free virtual images: Arista cEOS-lab, Juniper
  vJunos, and Cisco IOS-XE (Cisco Modeling Labs or a lab device).
- Security tests: a device outside `allowed_networks` is never contacted; a
  changed host key stops the poll; a SHOW input with `;`, a newline or an
  unknown pipe is refused; a result for another collector's device is
  rejected; secrets never appear in stored evidence.

## 5. Risks

- **Vendor quirks** (prompts, paging, banners, privilege levels) are most of
  the work, and every OS version can differ. Mitigation: start with three
  vendors, record real sessions, add vendors in point releases.
- **Legacy SSH** on old devices. Opt-in per profile, documented.
- **Large configs** (tens of thousands of lines on core devices): one read per
  poll, matching in memory on the collector; nothing large crosses to the
  server.
- **Collector down** means its devices go offline in the UI. Several
  collectors per device (failover) is left for later.

## 6. Questions for review

1. **Inventory in the UI, secrets on the collector** (D3) — or everything,
   device list included, in the collector's config file? Recommended: UI.
2. **Who adds devices** (D9): Admin (recommended) or Editor?
3. **Phase 1 vendors**: Cisco IOS/IOS-XE, Arista EOS, Juniper Junos — the
   right three for your customers? FortiOS is the likely alternative.
4. **Lab access**: are there real or virtual devices we can test against,
   especially Cisco IOS-XE?
5. **SaaS plans**: a device counts as one system (recommended, simplest), or a
   separate device limit per plan?
6. **Config backup**: keep it out of 2.0.0 (recommended; it means storing
   full configs with secrets on the server), or plan it for 2.1?
