# Design — Backup and restore (1.0.0)

**Status:** decided 2026-10-28 (recommendations accepted: always encrypted; no
web download; scheduled backups off by default with a dashboard warning until
configured; step 1 ships in 0.12.2).
**Target release:** 1.0.0 (step 1 may ship earlier, in 0.12.x)
**Author:** Yariv + Claude (design review)

---

## 1. Goal

Today a backup is a manual job described in the admin guide: stop the server,
copy `scm.db`, copy the key directory, start the server. Nothing checks it was
done, nothing checks the copy is usable, and restoring is "copy the files
back and hope the versions match". For a product that keeps audit evidence,
that is the largest gap between OpenSCM and "enterprise ready", and 1.2.0 high
availability builds on it (a standby is seeded from a backup).

1.0.0 makes backups **one command, scheduled, encrypted, verified**, and
restore **one command that refuses to do the wrong thing**.

What a server needs to come back exactly as it was:

| Part | Where (Linux) | Why it matters |
|---|---|---|
| Database | `/var/lib/openscm/scm.db` (WAL mode) | Everything: systems, tests, policies, results, reports, users, audit log |
| Server key pair | `/etc/openscm/keys/scmserver.key`, `.pub` | Agents from 0.10.4 pin it; sessions and every stored secret (tenant signing keys, SMTP, LDAP, SSO, webhooks) are derived from it. Without it a restored database is half usable and every agent has to be visited. |
| Config | `/etc/openscm/scmserver.config` | Port, TLS, trusted proxies, retention, … |

Out of scope: per-organization export and restore in SaaS (D7), copying
backups off the server to cloud storage (left to the customer's own tools in
1.0.0), point-in-time recovery.

## 2. Decisions proposed

### D1 — One encrypted file holds everything

A backup is a single file, `openscm-<host>-<UTC timestamp>.oscm-backup`:

```
age( tar.gz [
    manifest.json        -- OpenSCM version, edition (CE/SaaS), schema version,
                            created_at, host, SHA-256 of every other entry
    scm.db               -- consistent snapshot (D2)
    keys/scmserver.key
    keys/scmserver.pub
    scmserver.config
])
```

- **Always encrypted**, because it holds the server's private key: anyone with
  an unencrypted backup could impersonate the server to every agent and read
  every stored secret.
- Encryption is **[age](https://age-encryption.org)** with a passphrase
  (scrypt), through the pure-Rust `age` crate. It is a small, reviewed
  format, it cross-compiles with cargo-zigbuild, and a customer can decrypt a
  backup with the standalone `age` tool without OpenSCM — useful in a disaster
  and for auditors who want to check what is inside.
- The passphrase must be at least 12 characters. Losing it means losing the
  backups; the docs say so where it is set.

### D2 — Backups are taken while the server runs

The database snapshot uses SQLite's `VACUUM INTO`, which writes a consistent
copy of the database — including what is still in the WAL file — while the
server keeps serving. No stop, no downtime, no half-written copy. The snapshot
is opened and `PRAGMA integrity_check`ed before it goes into the archive.

### D3 — Ways to take a backup

1. **Command line**: `scmserver backup [--out FILE]`. Works while the server
   runs. The passphrase comes from `--passphrase-file`, the
   `OPENSCM_BACKUP_PASSPHRASE` variable, or a prompt. For cron jobs and
   customers' own backup tools.
2. **Scheduled**, configured in the config file:

   ```toml
   [backup]
   enabled         = true
   schedule        = "0 2 * * *"                    # cron, server time zone (as policy schedules)
   dir             = "/var/lib/openscm/backups"
   keep            = 7                              # newest N kept, older deleted
   passphrase_file = "/etc/openscm/backup.passphrase"  # readable by the service account only
   ```

   Each scheduled backup is verified (D5) right after it is written. A
   failure raises a notification to Admins and is available as an alert
   trigger (`backup failed`), so it reaches email, webhook or syslog like any
   other alert.
3. **Settings → Backup** shows the status: schedule, last backup, its size,
   whether it verified, the files kept. It has a **Back up now** button
   (writes to the same directory, same passphrase).

**No download from the web UI, and the passphrase is never set from the web
UI.** A stolen Admin session today can read the organization's data but not
the server's private key or the decrypted secrets. A download — or a
web-settable passphrase on backups written to disk — would turn that session
into the server key and every secret. Backup files are taken off the server
by the customer's own tools (rsync, their backup agent, `docker cp`), and the
docs show how.

### D4 — Restore is a command, with the server stopped

`scmserver restore FILE [--include-config]`

1. Refuses to run while the server is running. The server holds an exclusive
   lock file next to the database from 1.0.0; restore takes the same lock.
2. Decrypts, checks every entry against the manifest's SHA-256, runs
   `integrity_check` on the database.
3. Checks versions: a backup whose schema is **newer** than this server
   understands is refused ("install OpenSCM X.Y.Z or later first"). An older
   one is fine — the next start migrates it forward, as an upgrade would.
   A CE backup is not restored onto SaaS or the other way round.
4. Moves the current database, keys and config aside to
   `pre-restore-<timestamp>/` next to them, so a wrong restore can be undone.
5. Writes the database and key pair. The config is written only with
   `--include-config`: when restoring onto a new machine, its TLS paths and
   address usually differ.
6. Prints what was restored (backup date, version, schema) and what to check.
   The next server start writes a `backup.restored` audit entry naming the
   backup.

Not in the web UI: replacing the database under a running server ends every
session and request in flight, and a web restore would let an Admin session
install a database and key of its choosing.

### D5 — Verify

`scmserver backup verify FILE` decrypts, checks the manifest's hashes, opens
the database copy in a temporary directory, runs `integrity_check`, and
reports the version, schema, counts (organizations, systems, results,
reports) and the key's fingerprint, compared with the running server's. It
never touches the live database. Scheduled backups run it automatically
(D3). The docs recommend a restore drill on a spare machine each quarter,
with the steps.

### D6 — A server refuses a database newer than itself

Found while designing this: today an older `scmserver` opens a database
migrated by a newer one and runs against a schema it does not know. After a
package downgrade, or a restore of a newer backup by hand, that can silently
corrupt data. From now on the server refuses to start when
`schema_info.version` is higher than the newest migration it knows, and says
which version is needed. This stands on its own and can ship in 0.12.x.

### D7 — SaaS

- Server-level backups (D1–D5) are what the **platform operator** uses for
  disaster recovery. On SaaS, Settings → Backup is shown to the platform
  superuser only; organization Admins do not see it, because a backup holds
  every organization.
- **Per-organization export** (an organization taking its own data away, or
  restoring only itself) is a different feature with different problems:
  ids shared across tables, the shared schema, other organizations' rows. Not
  in 1.0.0. The REST API already lets an organization pull its compliance
  data and saved reports.

### D8 — Platforms

- Same commands on Linux, FreeBSD, macOS and Windows; paths follow each
  platform's existing fixed locations.
- Docker: the backup directory lives on the data volume;
  `docker exec openscm scmserver backup` works, and restore runs with the
  container stopped via `docker run --rm -v … scmserver restore …`.
- Windows: the passphrase file is created with the service account as its only
  reader, as the key file is.

### D9 — Audit

`backup.create` (scheduled, manual or command line, with size and result),
`backup.failed`, `backup.restored` (at the first start after a restore).

## 3. Build order

1. **Safety first**: the newer-schema guard (D6) and the server's lock file.
   Small; can ship in 0.12.x.
2. **Backup and verify on the command line**: the format (D1), the online
   snapshot (D2), `scmserver backup` and `backup verify` (D5).
3. **Restore**: `scmserver restore` (D4), including the version checks and
   the `pre-restore` copy.
4. **Scheduled backups and the Settings page**: `[backup]` config,
   retention, verify after write, notifications and the `backup failed`
   alert trigger, Back up now, audit, SaaS superuser-only (D3, D7, D9).
5. **Docs**: admin guide rewritten around the commands, off-host copying,
   restore drill, Docker and Windows.

## 4. Testing

- Round trip: back up a populated database while requests are writing to it,
  restore onto an empty server, compare every table, and check that an agent
  signed by the old key is still accepted and stored secrets still decrypt.
- Refusals: wrong passphrase; a changed byte anywhere in the file; a backup
  with a newer schema; CE onto SaaS; restore while the server runs.
- A backup from 0.12.x (schema 49) restored onto 1.0.0 migrates forward.
- The newer-schema guard: a database stamped one version ahead stops the
  server with a clear message.
- Retention keeps exactly `keep` files; a failed backup never deletes an older
  good one.
- `age` interoperability: a backup decrypts with the standalone `age` tool.
- Pages: Settings → Backup is Admin-only on CE and superuser-only on SaaS, and
  offers no download.
