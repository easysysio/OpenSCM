# Design — Remediation: fix scripts (1.1.0)

Status: draft, 2026-11-07. Decided with the user: fix scripts per test, a Fix
button on failed results, reuse `cmd_enabled` / `ps_enabled`, Editor and above.

## 1. Goal

Today a test's `remediation` field is text for a person to read. 1.1.0 lets a
test carry a script that fixes the problem, and lets an Editor run it on one
failing system from the results page.

The first version is deliberately one test on one system per click. "Fix all
failing", approvals and rollback come later (section 9).

## 2. What the user sees

- **Test editor:** two new optional fields under Remediation:
  - **Fix script (shell)** — for Linux, Unix and macOS, run with `/bin/sh`.
  - **Fix script (PowerShell)** — for Windows.
  The existing `remediation` text stays as the human explanation.
- **Results** (policy report and system report): a failed result gets a
  **Fix** button.
  - Hidden when the test has no script for that system's OS.
  - Gray, with a tooltip saying why, when:
    - the system does not allow it (`cmd_enabled` off for shell,
      `ps_enabled` off for PowerShell);
    - the agent is older than 1.1.0 and has not reported its settings;
    - the user is below Editor.
  - Shows "Fix queued" / "Fixing…" while a fix is pending for that
    system and test.
- **Confirm dialog:** the system name, the test, and the exact script that
  will run. Buttons: Run fix / Cancel.
- **Outcome:** after the agent reports back, the result row shows the fix's
  exit code and output (collapsed), and the test result itself is refreshed
  by a re-check (section 4, step 5).

## 3. Who may run a fix — and why reusing the CMD switch is safe

- **Editor and above** may queue a fix. Viewer and Runner see the button gray.
- **No new switch on the host.** A shell fix needs `cmd_enabled = true` in the
  agent's config, and a PowerShell fix needs `ps_enabled = true`.
- This does not widen anyone's power. An Editor can already write a test with
  a CMD element, which runs any command as root on every system with
  `cmd_enabled` on. A fix script is the same trust: Editor-written commands,
  run on hosts whose owner opted in locally.
- The docs and the agent config comment must say it plainly: turning on
  `cmd_enabled` / `ps_enabled` lets Editors run commands on this host,
  including fix scripts that change it.
- **The agent decides, not the server.** The server grays the button from what
  the agent last reported, but the agent checks its own config again before
  running anything. A server cannot turn fixes on for a host.

## 4. How a fix runs

1. The Editor clicks Run fix. The server copies the script into a new
   `fix_runs` row (section 5) with status `queued`, and writes an audit entry.
   At most one open fix per system and test; a second click is refused.
2. On the agent's next heartbeat (`POST /send`), the signed reply carries the
   queued fixes for that system in a new `fixes` list:
   `{ id, test_id, kind: "sh" | "ps", script, sha256, timeout_secs }`.
   The row becomes `sent`. The server never connects to agents, so this keeps
   the existing pull model.
3. The agent checks `kind` against its own `cmd_enabled` / `ps_enabled`, and
   the script against `sha256`. If either fails, it reports `refused` with the
   reason and runs nothing.
4. It runs the script as the agent's own user (root / SYSTEM), with
   `timeout_secs` (default 300; killed when it runs out). Then it sends
   `POST /fix_result` (Ed25519-signed like `/result`):
   `{ id, status: "done" | "failed" | "timeout" | "refused", exit_code, output }`.
   Exit code 0 = `done`. Output is capped at 64 KB.
5. Straight after, the agent re-runs that one test and sends its result the
   usual way, so the result page shows whether the fix worked. A fix that
   exits 0 but leaves the test failing is shown as such, not as success.
6. A fix not picked up within 24 hours becomes `expired`. An Editor can cancel
   a `queued` fix; a `sent` one can no longer be stopped.

## 5. Data model (schema v52)

- `tests`: `fix_sh TEXT`, `fix_ps TEXT` (NULL = none).
- `systems`: `cmd_enabled INTEGER`, `ps_enabled INTEGER` — NULL until an agent
  1.1.0+ reports them (button gray: "agent too old").
- New table `fix_runs`:

  | Column | Notes |
  |---|---|
  | id, tenant_id, system_id, test_id | FK to systems and tests, ON DELETE CASCADE |
  | kind | `sh` or `ps` |
  | script, script_sha256 | copied at queue time, so later edits to the test do not change a queued or past fix |
  | requested_by, requested_at | user id, timestamp |
  | status | `queued`, `sent`, `done`, `failed`, `timeout`, `refused`, `expired`, `cancelled` |
  | sent_at, finished_at, exit_code, output | filled as the run progresses |

  Not the `commands` table: its key (tenant, system, test) would collide with
  a TEST command for the same test, and fixes need history.

## 6. Agent changes (scmclient 1.1.0)

- `SystemInfo` in the heartbeat gains `cmd_enabled` and `ps_enabled`.
- Reads `fixes` from the heartbeat reply. Older agents ignore the field, so
  the server only queues fixes for systems that reported the settings.
- Runs shell fixes with `/bin/sh -c` on Linux, Unix and macOS, and PowerShell
  fixes with `powershell -NoProfile -NonInteractive -Command` on Windows —
  the same way as the CMD and PS elements.
- New signed `POST /fix_result`, then the re-check from section 4.

## 7. Audit and alerting

- Audit entries: `fix.queue` {system, test, kind, script_sha256},
  `fix.cancel`, `fix.result` {status, exit_code}. The script itself stays in
  `fix_runs`, not in the audit log.
- Alerting is out of scope for 1.1.0; a "fix failed" trigger can be added later.

## 8. Where tests travel

- Test export / import and test copy carry `fix_sh` / `fix_ps`.
- **Policy Store (SaaS):** store tests do not ship fix scripts in 1.1.0. A script
  written outside the organization would run as root on its hosts; that needs
  its own review step first.

## 9. Not in 1.1.0

- Fix all failing systems for a test or a policy (blast-radius limits).
- A second person approving a fix.
- Rollback scripts and dry-run.
- Fixes through the REST API.
- Network devices and agentless systems (2.x).

## 10. Open questions

- Is 300 seconds the right default timeout, and should a test be able to set
  its own?
- Should a fix also be possible on a result that is not failed (e.g. to
  re-apply a setting), or failed only?
