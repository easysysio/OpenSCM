# Design — REST API, v1beta1 (0.12.0)

**Status:** decided 2026-10-27 (recommendations accepted: a role per token
capped at the owner's; 90-day default expiry with "never" available; scope as
in D3). All four steps built.
**Target release:** 0.12.0
**Author:** Yariv + Claude (design review)

---

## 1. Goal

Everything in OpenSCM is reachable only through the web pages today. Customers
who automate — CI pipelines that scan a host before it goes live, SIEMs and
dashboards that pull compliance data, provisioning that approves new systems —
have nothing to call. The API gives them a stable, documented, token-
authenticated way in, for both CE and SaaS.

It is published as **`/api/v1beta1`**: usable, documented, and allowed to
change in 0.x releases (each change noted in the CHANGELOG). It becomes
`/api/v1`, frozen, once a real integration has used it — not at a date and not
tied to 1.0 (see the roadmap decision of 2026-08-25).

## 2. Decisions proposed

### D1 — Authentication: API tokens, never the session cookie

- A token belongs to a **user**, in that user's organization, and has a
  **role of its own, at most the owner's** (Viewer, Runner, Editor or Admin).
  A dashboard gets a Viewer token; a CI job that triggers scans gets a Runner
  token, even if the person who made it is an Admin.
- Sent as `Authorization: Bearer oscm_api_…`. The session cookie is **not**
  accepted on `/api`: no cookie means no cross-site request forgery to defend
  against, and a stolen browser session cannot drive the API.
- Format: `oscm_api_` + 32 random bytes (base64url) — a different prefix from
  enrollment tokens (`oscm_`), so the two cannot be confused and secret
  scanners can tell them apart. Stored as a SHA-256 hash; only a short prefix
  is kept for display. Shown once, at creation.
- **Expiry** chosen at creation: 30, 90 (default) or 365 days, or none.
- Checked on **every request** against the current state, like sessions
  (`auth::validate_session`): the owner still exists, the owner's current role
  still covers the token's role (a downgraded user's tokens shrink with them),
  the organization is not suspended, the token is not revoked or expired.
- `last_used_at` and `last_used_ip` recorded (at most once a minute per token).
- Created, listed and revoked on a new **API tokens** page. Users manage their
  own; Admins see and can revoke every token in the organization.
- SaaS superusers get **no cross-organization API** in v1beta1. Platform
  administration stays in the web UI.

### D2 — One organization per token

The organization comes from the token; it never appears in a URL. Every
query is scoped to it, exactly as the pages are.

### D3 — What v1beta1 covers

Chosen for the integrations people actually ask for — read compliance, trigger
scans, onboard systems — and nothing that is risky to get wrong in a beta.

| Area | Read | Write | Role to write |
|---|---|---|---|
| Systems | list, get (incl. telemetry, agent version, groups, online state) | approve, delete, set groups, queue agent upgrade | Editor (approve, delete, groups — as the pages), Admin (upgrade) |
| Groups | list, get with members | — | |
| Tests | list, get with conditions | — | |
| Policies | list, get with tests and linked groups; compliance summary | **run now**; import (the existing policy export JSON) | Runner (run), Editor (import) |
| Compliance | per system: latest result per test, with evidence; per policy: per-system scores | exclude / unexclude a finding, with reason | Editor |
| Reports | list saved snapshots, get one (JSON), download PDF | save a snapshot | Runner |
| Audit log | list, filtered by time and action | — | read needs Admin |

**Not in v1beta1:** users, settings, SSO, LDAP directories, enrollment tokens,
alert rules, creating or editing individual tests and conditions (import a
policy instead). Each is a later, additive version if asked for.

Reads need Viewer unless noted.

### D4 — Conventions

- JSON in and out, `snake_case`, UTF-8. Timestamps ISO 8601 UTC with `Z`.
  IDs are integers.
- **Lists** return `{"data": [...], "next_cursor": "…" | null}`. Cursor
  pagination (opaque, based on the id), `limit` default 100, maximum 1000.
  Cursors stay correct while rows are added, which offset pages do not.
- **Errors** return `{"error": {"code": "not_found", "message": "…"}}` with the
  matching status: 400 validation, 401 bad or missing token, 403 role too
  low, 404 not found (also for another organization's ids), 409 conflict,
  422 plan limit reached (SaaS), 429 rate limited, 503 before install.
- **Writes** that start work (run a policy, queue an upgrade) return
  `202 Accepted` with what was queued; the results arrive as agents report.
- No API-specific shape for compliance data where one exists: the report JSON
  uses the same fields as the PDF and the pages.

### D5 — Limits

- **Rate:** 600 requests a minute per token (`rate_limit::Limiter`), 429 with a
  `Retry-After` header beyond that.
- **SaaS plan limits** apply to API writes exactly as to pages: approving a
  system or importing a policy past the plan's limit is a 422.

### D6 — Audit

Every API **write** is recorded in the audit log as the token's owner, with
`via: "api"` and the token's name. Token creation and revocation are recorded.
Reads are not (the log would drown in polling).

### D7 — Documentation

- A hand-written **OpenAPI 3.1** file, `docs/api/openapi.yaml`, published
  with the docs site, with a page explaining tokens and examples (curl).
- A test fails if a route exists in the router but not in the spec, or the
  other way round, so the spec cannot drift.
- Rejected: generating the spec from code (`utoipa`). It adds a derive
  framework and a dozen crates for something a test can keep honest.

### D8 — Code structure

- `scmserver/src/api/` — one module per area, its own router merged under
  `/api/v1beta1` in `create_core_router`, so both editions get it.
- The queries behind the pages move into shared functions that **both** the
  pages and the API call (several already exist: `fetch_system_report_data`,
  `execute_policy_run_logic`, `apply_policy_import`). The API never has its
  own copy of how compliance is computed.
- Security headers, the init guard and trusted proxies apply as everywhere.

### D9 — Schema

v48 → v49: `api_tokens` (`id`, `tenant_id`, `user_id`, `name`, `prefix`,
`token_hash`, `role`, `created_at`, `expires_at`, `last_used_at`,
`last_used_ip`, `revoked_at`). Deleting a user deletes their tokens.

## 3. Build order

1. Tokens: schema, the API tokens page, Bearer authentication, rate limit,
   error format.
2. Read endpoints, moving each page's query into a shared function as it goes.
3. Write endpoints, with audit and plan limits.
4. OpenAPI file, the drift test, the docs page.

Each step ships tested; 0.12.0 is cut when all four are in.

## 4. Questions for review (answered 2026-10-27)

1. Token roles (D1): a role per token, capped at the owner's — or simply the
   owner's role?
2. Expiry (D1): 90 days by default with "never" available — or require an
   expiry?
3. Scope (D3): is anything missing that a first integration would need, or
   anything here you'd rather leave out?
